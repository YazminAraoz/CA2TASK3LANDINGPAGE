Phase 1

The Original Concept (Human Input & Initial Hook)

Every software project starts with a real-world pain point. For BAY WATCH, the genesis came from observing independent rural garages dealing with severe administrative bottlenecks due to continuous phone interruptions.

Raw Human Input / Context:

  • Operations: Tom Kehoe runs the garage with 4 mechanics servicing ~25 cars a day. Bríd runs the office.
  • The Problem: Customers phone ~60 times a day asking for updates. When Bríd is busy, mechanics stop working to answer phones, costing 90 minutes of mechanic time daily.
  • Forgotten Cars: Cars waiting for parts get forgotten and sit for 5+ days without customer updates.
  • Core Views Required:
    • Workshop: Wall tablet view for greasy hands, large targets, zero typing, 1-tap stage advancement.
    • Customer: Secure status lookup portal using Job Number + Registration (strict privacy, plain-English updates).
    • Office: Grouped by stage, auto-alerts in red for parts waiting > 2 days, collection counters.
  • Generic Niche Target: Rural independent owner-run garages in Leinster (1 owner + 2-5 mechanics, 15-30 cars/day, no full-time receptionist).
Phase 2

Building the Functional Alpha App

Using the human hook as the foundation, Gemini was prompted to create a fully working single-file HTML/CSS/JavaScript web application featuring client-side persistence and role-based access control.

Prompt Used:

Build a single-file web app (HTML, CSS and JavaScript in one file, no external libraries, works on a phone) called BAY WATCH, for Kehoe's Garage, Enniscorthy, Co. Wexford... [incorporating workshop, customer, and office views with localStorage].

Evolution & Refinement Prompts:

  • Prompt: "Change it so if a customer access only can view the customer portal. As it is a demo, the password and log in is showing and disposable. Make a part with person assigned only on the workshop part."
  • Prompt: "Make it more easy to assign and reassign mechanic. Think these will be people with greasy hands and busy environment. Also make it more design savy."
Phase 3

Transitioning to a SaaS Landing Page

Once the core alpha logic was verified and tested, the focus shifted to marketing the solution to independent rural garage owners across Leinster.

Prompt Used:

Build index.html: a landing page that sells the generic version of BAY WATCH, not to Kehoe's Garage and not to everyone - to your Task 1 niche (Rural independent owner-run garages in Leinster)... Include headline, problem quotes, 3-step guide, pricing assumption (€199 setup + €59/month), and waiting list form.

Design & UX Iteration Prompts:

  • Prompt: "Make it more UX friendly. Exclude any task. Make the app from before like a real landing page for these service."
  • Prompt: "Add more colour and cool design car brand inspired, make it mobile first. Eliminate testimonial. Make it true to the app designed."
  • Prompt: "Make the model from tablet interactive and the same as demo with interaction but not dynamic sizing. Add contact formulation like before."
Phase 4

Key Technical Takeaways

  • Zero Dependencies: Built entirely in native HTML5, modern CSS3 (Flexbox/Grid), and Vanilla JavaScript for maximum reliability and zero build configuration.
  • State Persistence: Utilized browser localStorage so demo job updates persist across reloads.
  • Mobile-First & Touch Optimized: Designed with giant touch targets (>58px height) to accommodate greasy hands and wall tablets.
